# Credentials and workspace administration

## Contents

- Preconditions: authentication planes and API-key fields
- Inspect: metadata and authentication hard stop
- Preview and approval; execute
- Verify: protected REST test and scope limits
- Recovery and cleanup; evidence

## Goal

Configure or diagnose credential profiles, workspace scope, users, API keys, or platform credentials without placing secrets in repository files, logs, evidence, or broad unintended scope.

## Preconditions

- Identify installation/environment, credential type, intended workspace/account scope, least-privilege role, profile name, and requested administrative outcome.
- Determine whether the machine has an OS keyring or needs an approved headless backend.
- Never ask the user to paste a reusable secret into a tracked file or ordinary chat evidence.

### Keep two authentication planes separate

The local CLI profile authenticates the operator's tool calls. A platform-held connection
GUID lets a process authenticate at runtime; it does not replace or invalidate a working
CLI login. A workspace GUID scopes calls, while a connection GUID identifies a credential
resource. Verify the resource type and name through restricted/list metadata before binding
it; a GUID-shaped value alone is not identity proof. Credential summaries use `gid`, not
`id`; verify template/envelope keys against the actual DTO. A null projection is not evidence
of absence. Do not repurpose an unrelated connection based only on its generic REST template.

Recover known setup and sanitized receipts before asking the operator to repeat onboarding.
Keep emails or user IDs local when they are not needed for the decision. Request only the
minimal non-secret connection metadata; inspect role permissions locally rather than ask
for a raw account/credential dump.

### PROCESIO API-key field mapping

Keep these values separate; the product and CLI use different labels:

| Meaning | PROCESIO UI | CLI |
|---|---|---|
| Local alias for choosing the credential later | Not applicable | `--name`, for example `contoso-demo` (synthetic alias) |
| Public identifier sent in the `key` request header | **Key Handle** | Secure prompt `PROCESIO Key Handle`, or `--key` for non-interactive setup |
| One-time secret sent in the `value` request header | API key value | Secure prompt `PROCESIO API key value (shown once)`, or `--value` |
| Workspace scope | Workspace ID | `--workspace-id` |

The **Key Handle is not the local profile name, workspace name, or a user-chosen label**. Copy it exactly from the API-key creation result. Prefer the secure prompts; command-line `--key` and `--value` arguments can leak through shell history and process listings.

The secret is generated by PROCESIO when the API key is created and displayed once; do
not invent it or substitute a password, label, workspace GUID, or Key Handle. Losing it
requires separately approved replacement, not retrieval by printing credential-store internals.

## Inspect

1. List profiles and readiness metadata only; do not read or echo secret values.
2. Read environment/workspace inventory with an existing least-privilege profile where possible.
3. Distinguish user/password session reach from workspace-scoped API-key reach.
4. For platform credentials, inspect template, non-secret fields, dependent resources, and current test status.

### Authentication hard stop

- `mode: apikey` or `mode: userpass` reports the stored profile type only. It is not evidence that authentication worked.
- If `check-auth` returns `authenticated: false`, or its probe returns `401`/`403`, stop all remote PROCESIO calls. Do not try alternate endpoints; they cannot confirm the workspace while the same credential is rejected.
- The only allowed follow-up diagnostics are local and non-secret: `show-credential`, `list-credentials`, and `show-environment`.
- Do not inspect credential-store internals, dump environment variables, print commands containing secrets, or search source code for a way around the failed check.
- If the non-secret metadata is correct, ask the operator to recreate or re-enter the API key in this exact order: **Key Handle**, then **API key value**, for the intended workspace. Retry `check-auth` before any other API call.
- Until a server response succeeds, report the requested workspace as **configured but not confirmed**.

## Preview and approval

- Show profile name/type/scope and storage backend—not secret content.
- For user/role/API-key/credential creation, update, default switch, removal, or rotation, state affected workspace and dependents.
- Removing or replacing a credential can break many processes; inventory references first.

## Execute

- Use secure prompt/keyring-backed actions for secret capture.
- Store environment/profile binding separately from the secret.
- Make one narrow administrative change.
- Do not print the command with the secret substituted, and redact provider responses.

## Verify

- Run the cheapest read-only auth/health check with the named profile and intended workspace.
- Continue only when the result explicitly says `authenticated: true`; a status code or profile mode must not be reinterpreted as success.
- Test a platform credential through its dedicated connection/test action when available.
- Verify granted scope by one permitted read. An expected-denial test requires an explicitly authorized target and action. Never probe a forbidden workspace or tenant merely to prove least privilege.
- Re-fetch non-secret profile/credential metadata and confirm dependents still resolve.

### REST connection test scope

For a PROCESIO self-API connection, the REST credential's auth Key is the literal `value`,
its Value holds the secret, and placement is Header. Supply `key` (matching Key Handle)
and `workspaceid` separately in test headers. Test-only headers do not establish runtime
Call API headers; verify both configurations without exposing the secret.

Use an approved protected read endpoint, not a public health page, for an authentication
test. HTTP 200 proves access to that endpoint; it does not prove read-only authorization,
all endpoint permissions, or a process run. API keys inherit their owner's permissions;
a Read Only label does not impose scope. A test 401/403 is not proof the independent CLI
profile failed: stop testing that connection and inspect its configuration/scope locally,
without automatic key regeneration or privilege escalation. A failed CLI `check-auth`
still invokes the hard stop above. Test approval never authorizes scanner activation or runs.

## Recovery and cleanup

For routine rotation of an unexposed credential, use an approved overlap/recovery plan until dependents pass. Never restore a disclosed or revoked credential to recover availability. After exposure, stop affected automation under the separately approved containment plan, preserve the incident, rotate/revoke the exposed value and prove denial of the old value and acceptance of the replacement through a bounded approved path. Redaction alone is not recovery. Revoke temporary keys after testing; do not remove the only administrative profile without a tested recovery path.

For a newly created disposable profile that has never authenticated, remove the local profile, create a fresh key while the intended workspace is selected, store the new **Key Handle** and API key value through the secure prompts, and repeat only `check-auth`.

## Evidence

Return environment/workspace IDs, profile/credential name and type, storage backend category, readiness/auth test result, verified scope, dependents checked, and rotation/revocation status. Never include secret values.
